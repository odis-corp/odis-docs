# Implementation Plan: Облачное хранилище файлов

**Branch**: `001-cloud-storage-requirements` (фактическая git-ветка: `feature/ODIS-1`) | **Date**: 2026-11-06 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/001-cloud-storage-requirements/spec.md`

## Summary

Требуется построить самодостаточное облачное хранилище файлов для личного и малого командного использования: до 10 пользователей, до 1 ТБ данных, до 10 000 объектов в папке. Ядро — файлы и папки, права и группы, публичные ссылки, версии и корзина, синхронизация между устройствами с явным разрешением конфликтов, метаданные и поиск, комментарии, администрирование и аудит, выгрузка учётной записи и резервное копирование с проверяемым восстановлением.

Технический подход: один серверный бинарник на Go с PostgreSQL как хранилищем метаданных и локальным файловым хранилищем содержимого, адресуемым по SHA-256; веб-клиент на React; CLI-агент синхронизации на Go; развёртывание одним узлом через Docker Compose. Сквозное шифрование — клиентское, с явно отключаемыми серверными возможностями. Совместное редактирование документов и федерация между установками — желательные (SHOULD) возможности, вынесенные в отдельные фазы.

## Technical Context

**Language/Version**: Go 1.25 (сервер, CLI-агент синхронизации, фоновые задачи); TypeScript 5.x + React 19 (веб-клиент)

**Primary Dependencies**:
- Сервер: стандартная библиотека `net/http` + `chi` (маршрутизация), `pgx/v5` (PostgreSQL), `golang-migrate` (миграции), `argon2id` (`golang.org/x/crypto`), `pquerna/otp` (TOTP), `tus`-совместимый обработчик докачки (собственная реализация подмножества протокола), `zerolog` (структурные журналы)
- Веб: Vite, React 19, TanStack Query, React Router, `@uppy/tus` (докачка), `yjs` + `y-websocket` (только для SHOULD-фазы совместного редактирования)
- Тесты: `go test` + `testcontainers-go`, Playwright, `k6`

**Storage**:
- Метаданные: PostgreSQL 17 (права, версии, ссылки, комментарии, журнал, очередь фоновых задач)
- Содержимое: локальная файловая система, контентно-адресуемое хранилище (SHA-256, двухуровневое шардирование каталогов), атомарная фиксация через `fsync` + `rename`
- Абстракция хранилища допускает последующую замену на S3-совместимое без изменения модели метаданных

**Testing**: **TDD обязателен** (решение от 2026-11-06): для каждой единицы поведения тест пишется первым, запускается и падает до реализации; «зелёный» тест без предшествующего падения не считается выполненным. Уровни: `go test` (юнит), интеграционные тесты с реальным PostgreSQL в контейнере, contract-тесты по `contracts/openapi.yaml`, Playwright (E2E по сценариям `quickstart.md`), `k6` (SC-019)

**Target Platform**: Linux-сервер (Docker Compose, один узел); веб-браузеры (актуальные Chrome/Firefox/Safari/Edge); CLI-агент синхронизации для Windows, macOS, Linux

**Project Type**: веб-приложение с серверным API + отдельный CLI-клиент синхронизации (монорепозиторий)

**Performance Goals**: открытие папки с 1 000 объектов — p95 ≤ 2 с; отклик на действие — p95 ≤ 0,5 с; поиск — p95 ≤ 2 с; начало скачивания — p95 ≤ 3 с; не менее 95% замеров в планке (SC-019)

**Constraints**: один узел; ≤ 10 пользователей; ≤ 1 ТБ суммарно; ≤ 10 000 объектов в папке; RPO ≤ 24 ч; RTO ≤ 4 ч; отсутствие молчаливой потери данных при конфликтах; работа при нестабильной сети и офлайн; отсутствие обязательных внешних сервисов

**Scale/Scope**: 10 областей требований, 104 функциональных требования (91 MUST / 13 SHOULD), 22 критерия успеха, 18 краевых случаев

**Structure Decision**: монорепозиторий с одним серверным бинарником и отдельным CLI-агентом. Выбрано потому, что: (а) сервер и агент делят модель синхронизации и должны версионироваться вместе; (б) веб-клиент собирается статически и раздаётся тем же бинарником, отдельный фронтенд-сервер не нужен при 10 пользователях; (в) отсутствие микросервисов соответствует гейтам G4 и G5. Альтернатива «backend/ + frontend/ + sync/ как три независимых проекта» отвергнута: три версии модели синхронизации вместо одной.
