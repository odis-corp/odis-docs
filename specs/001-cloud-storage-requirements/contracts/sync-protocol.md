# Contract: протокол синхронизации

**Feature**: `specs/001-cloud-storage-requirements` | **Date**: 2026-11-06
**Связанные требования**: FR-044…FR-052, FR-019…FR-026, SC-003, SC-006
**Решения**: `research.md` R4, R5, R6, R7

Назначение: определить, как устройство и сервер приходят к согласию о состоянии файлов, не теряя данные и не полагаясь на системные часы.

---

## 1. Базовые принципы

1. **Порядок задаёт сервер, а не время.** Изменения нумеруются монотонным `seq` в `change_log`. Устройство применяет их строго по возрастанию. Отметка времени файла (`mtime`) переносится как атрибут, но **никогда** не используется для определения того, какое изменение «новее» (FR-047).
2. **Устройство не пишет в хранилище напрямую.** Любая локальная правка превращается в операцию в `sync/push`; сервер проверяет права, базовую версию и фиксирует результат.
3. **Конфликт — это не ошибка, а состояние.** Обе версии сохраняются; проигравших нет (FR-046).
4. **Идемпотентность.** Каждая операция несёт `client_op_id`; повторная отправка с тем же идентификатором не создаёт вторую версию.
5. **Докачка вместо повтора.** Содержимое передаётся сессией загрузки; уже переданные байты не передаются заново (FR-020).

---

## 2. Регистрация устройства

```text
POST /api/v1/devices            (Bearer: пользовательский токен)
{ "name": "Ноутбук", "platform": "windows" }
→ 201 { "device_id": "...", "device_token": "..." }
```

- `device_token` показывается один раз; на сервере хранится только хеш.
- Устройство получает собственный `device_id`, который используется во всех последующих операциях.
- Отзыв устройства (`DELETE /api/v1/devices/{id}`) немедленно прекращает синхронизацию; локальные данные на устройстве остаются, но новые изменения не принимаются (FR-084 по аналогии).

---

## 3. Цикл синхронизации

Устройство выполняет цикл:

```text
1. HEAD локального состояния → собрать локальные операции
2. GET /sync/changes?since=<last_seq>   → применить удалённые изменения
3. POST /sync/push                       → отправить локальные операции
4. Повторять шаг 2, пока latest_seq > last_seq
5. Сохранить last_seq
```

Порядок «сначала принять чужое, потом отправить своё» фиксирован: иначе устройство будет отправлять операции, основанные на устаревшей базе, и получит ложные конфликты.

### 3.1. Применение изменений

Для каждого элемента `changes`:

| `op` | Действие на устройстве |
|---|---|
| `upsert` | создать или обновить локальную запись; если содержимого нет — поставить в очередь загрузки |
| `delete` | удалить локально; если есть несохранённые правки — создать конфликтную копию |
| `rename` | переименовать; если целевое имя занято локально — конфликтная копия |
| `move` | переместить; если целевая папка отсутствует — создать её локально как «ожидающую» |
| `restore` | вернуть из локальной корзины |
| `conflict` | создать/обновить конфликтную копию и пометить исходный объект |

Изменения применяются в одной транзакции на пачку; `last_seq` сдвигается только после успешного применения всей пачки.

### 3.2. Отправка изменений

```text
POST /sync/push
{
  "device_id": "...",
  "operations": [
    { "client_op_id": "d-17f3", "op": "upsert", "node_id": "...",
      "base_version_id": "...", "sha256": "...", "size": 1048576,
      "mtime": "2026-11-06T10:00:00Z" }
  ]
}
```

Ответ по каждой операции: `applied` | `conflict` | `rejected`.

- `rejected` — нарушены права, имя недопустимо, квота исчерпана, объект не существует. В `reason` — машинный код.
- `conflict` — `base_version_id` не совпадает с текущей версией на сервере. В ответе приходят `node` (текущая версия) и `conflict_node` (сохранённая версия устройства).

## 4. Обнаружение и разрешение конфликтов

### 4.1. Условие конфликта

Конфликт возникает, когда одновременно выполнены условия:

1. устройство предлагает `upsert` для узла с `base_version_id = V`;
2. текущая версия узла на сервере — не `V`.

Это **не** зависит от `mtime` и от порядка поступления операций (FR-047).

### 4.2. Что происходит

```text
Сервер:
  1. Сохраняет предложенную версию как отдельный блоб (если хеша ещё нет)
  2. Создаёт узел-копию:
       name = "<исходное имя> (конфликт, <устройство>, <YYYY-MM-DD HH-MM>)"
       state = 'conflict'
       conflict_of = <исходный узел>
  3. Помечает исходный узел state = 'conflict'
  4. Возвращает обе версии клиенту
```

Инварианты:

- **Обе версии существуют и доступны для скачивания.** Ни одна не удаляется автоматически.
- Конфликтная копия подчиняется правилам имён (R7): имя нормализуется, при совпадении добавляется суффикс.
- Состояние `conflict` снимается, когда пользователь выбирает основную версию:
  - `POST /nodes/{id}/resolve` с `keep: "current" | "conflict"`; выбранная становится текущей, вторая остаётся как обычный файл либо удаляется в корзину по выбору пользователя.

### 4.3. Запрещённые стратегии

- **Last-write-wins по `mtime`** — запрещено: нарушает FR-046 и SC-003.
- **Молчаливое переименование без пометки** — запрещено: пользователь не узнает о конфликте.
- **Блокировка файла на время конфликта** — запрещено: делает офлайн-работу невозможной (FR-045).

---

## 5. Переименование и перемещение

- Переименование передаётся как `op: "rename"` с `base_version_id`, если содержимое не изменилось. Устройства получают `rename` и меняют путь локально **без повторной передачи содержимого** (FR-050).
- Перемещение передаётся как `op: "move"` с новым `parent_id`. Сервер отвергает перемещение, создающее цикл (FR-018).
- При перемещении в папку, где уже есть объект с таким же `name_folded`, сервер возвращает `rejected` с `reason: name_conflict`; клиент обязан предложить переименование, а не перезаписывать.

---

## 6. Имена и регистр

- Локальное сравнение имён на устройстве **обязано** использовать ту же нормализацию, что и сервер: Unicode NFKC + case folding (R7).
- Если целевая платформа не допускает имя (запрещённые символы, служебные имена вроде `CON`, `NUL`, `thumbs.db`), устройство:
  1. заменяет недопустимые символы;
  2. добавляет суффикс при совпадении;
  3. сообщает пользователю, какое имя было изменено и почему (FR-017);
  4. фиксирует событие в локальном журнале, чтобы изменение не «мигрировало» обратно на сервер как новое имя.

## 7. Полная сверка (resync)

Требуется, когда:

- `GET /sync/changes` вернул `resync_required: true` (курсор старше горизонта ретенции);
- устройство потеряло локальную базу;
- сервер сообщил о несовместимой версии протокола.

Порядок:

```text
1. GET /sync/tree?cursor=...   → полный список узлов и версий (постранично)
2. Сравнить с локальным состоянием по (node_id, version_id)
3. Недостающее — скачать; лишнее — переместить в локальную корзину, не удаляя сразу
4. Зафиксировать новый last_seq
```

**Запрещено** при полной сверке удалять локальные файлы, которых нет на сервере: они перемещаются в локальную корзину с пометкой «отсутствует на сервере», чтобы пользователь мог восстановить их (защита от потери данных).

---

## 8. Офлайн-работа

- Устройство ведёт локальный журнал операций, пока нет связи.
- При восстановлении связи журнал отправляется в исходном порядке; `client_op_id` обеспечивает идемпотентность при повторах.
- Если операция ссылается на объект, которого на сервере уже нет, она возвращается как `rejected` с `reason: parent_missing`; устройство создаёт локальную папку-«сироту» и показывает её пользователю, а не выбрасывает данные.
- Ограничение: журнал офлайн-операций не ограничен по времени, но ограничен по объёму (настраивается); при переполнении устройство останавливает синхронизацию и требует внимания пользователя, а не отбрасывает старые операции.

---

## 9. Целостность содержимого

- Клиент вычисляет SHA-256 перед отправкой и передаёт его в `upsert`.
- Сервер вычисляет SHA-256 при приёме и сравнивает; при несовпадении операция возвращается `rejected` с `reason: hash_mismatch`, а блоб не фиксируется (FR-024).
- Скачивание сопровождается сверкой хеша на клиенте; при несовпадении файл помечается повреждённым и запрашивается повторно.

---

## 10. Совместимость и версионирование протокола

- Версия протокола передаётся в заголовке `X-Sync-Protocol`.
- Несовпадение мажорной версии — отказ с `reason: protocol_incompatible`; устройство обязано обновиться, а не пытаться работать в несовместимом режиме.
- Сервер обязан поддерживать предыдущую мажорную версию не менее одного релизного цикла.

## 11. Проверяемые сценарии (для contract-тестов)

| # | Сценарий | Ожидание |
|---|---|---|
| S1 | Устройство A изменяет файл, B онлайн | B получает `upsert` и новый `version_id` |
| S2 | A и B офлайн меняют один файл | После связи: обе версии сохранены, оба узла в состоянии `conflict`, пользователь может выбрать основную |
| S3 | A переименовывает, B переименовывает иначе | Конфликт имён разрешается копией; содержимое не теряется |
| S4 | `mtime` на B «новее», но изменение A пришло позже | Порядок определяется `seq`, а не `mtime`; конфликт, а не перезапись |
| S5 | Устройство отправило операцию дважды | Вторая попытка возвращает тот же результат, дубликата нет |
| S6 | Курсор устройства старше ретенции | `resync_required: true`, полная сверка, локальные лишние файлы — в корзину, не удаляются |
| S7 | Имя недопустимо на Windows | Имя заменено, пользователь уведомлён, данные на месте |
| S8 | Обрыв посреди передачи 2 ГБ | `HEAD` возвращает смещение, передача продолжается с него |
| S9 | Файл загружен, но чтение началось до фиксации | Читатель получает «не готов» либо ждёт, но не получает половину файла |
| S10 | Отозван доступ к папке у устройства | Следующий `push` → `rejected: forbidden`; локальные данные не отправляются |
