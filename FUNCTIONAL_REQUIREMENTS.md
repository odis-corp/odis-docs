# Функциональные требования: облачное хранилище файлов

**Версия**: 1.0

**Дата**: 2026-11-06

**Статус**: Готово к использованию как вход в реализацию

**Область**: функциональные требования к собственной системе облачного хранения файлов

---

## 1. Назначение и область применения

Документ описывает, **что** должна делать система облачного хранения файлов. Он не описывает, **как** её строить: технологии, архитектура, протоколы, форматы хранения и схемы данных сознательно не рассматриваются.

Документ предназначен для трёх задач:

1. **Сравнение** готовых решений (Яндекс.Диск, Google Drive, Dropbox и их открытые аналоги) с собственными потребностями по единой рамке.
2. **Обсуждение** объёма и границ работ без споров о терминах.
3. **Реализация** — как исходный перечень того, что должно быть сделано, с проверяемыми формулировками.

Требования опираются на возможности уже существующих систем, но **не копируют их ограничения**. Если какая-то возможность отсутствует у одного из референсов, это не значит, что она не нужна; если присутствует — не значит, что нужна.

### 1.1. Заявленный масштаб

| Параметр | Значение |
|---|---|
| Пользователей | до 10 |
| Суммарный объём данных | до 1 ТБ |
| Объектов в одной папке | до 10 000 |
| Глубина вложенности | до 32 уровней |
| Длина полного пути | до 4096 символов |
| Потеря данных при сбое (RPO) | не более 24 часов |
| Восстановление после сбоя (RTO) | не более 4 часов |

Требования MUST выполняться в этих пределах. Выход за них — предмет отдельного решения, а не подразумеваемое расширение.

## 2. Как читать документ

### 2.1. Уровни обязательности

| Ключевое слово | Значение |
|---|---|
| **MUST** | Обязательно. Без этого система не соответствует требованиям. |
| **SHOULD** | Желательно. Отклонение допустимо, но должно быть осознанным и обоснованным. |
| **MUST NOT** | Запрещено. Нарушение — дефект, а не компромисс. |

### 2.2. Нумерация

- **FR-NNN** — функциональное требование.
- **SC-NNN** — измеримый критерий приёмки.
- **US-N** — пользовательская история.

Номера стабильны: они используются для трассировки в задачах, тестах и приёмочных проверках.

### 2.3. Что считается выполненным

Требование выполнено, когда его можно проверить, не задавая уточняющих вопросов. Если формулировка допускает два разных прочтения — это дефект документа, а не вопрос к реализации.

## 3. Термины

| Термин | Значение |
|---|---|
| **Объект** | Файл или папка в хранилище. |
| **Владелец** | Пользователь, которому принадлежит объект и который может передать его другому. |
| **Право доступа** | Разрешение конкретному пользователю или группе выполнять действия над объектом. |
| **Уровень доступа** | Просмотр, комментирование, редактирование или полный контроль. |
| **Версия** | Сохранённое состояние содержимого объекта с указанием автора и времени. |
| **Корзина** | Место временного хранения удалённых объектов до окончательного удаления. |
| **Ссылка** | Правило внешнего доступа к объекту без учётной записи. |
| **Ссылка на загрузку** | Ссылка, позволяющая положить файл в папку, но не читать её содержимое. |
| **Конфликт** | Ситуация, когда один объект изменён в двух местах независимо друг от друга. |
| **Квота** | Допустимый объём данных для пользователя или группы. |
| **Сквозное шифрование** | Режим, при котором содержимое зашифровано на стороне пользователя и недоступно системе. |
| **Выгрузка** | Получение всех данных учётной записи одним архивом. |

## 4. Пользовательские сценарии

Двенадцать историй задают пользовательскую ценность. Каждая проверяется независимо от остальных.

### US-1. Хранение и упорядочивание файлов — P1

Пользователь загружает файлы и папки, раскладывает их по структуре, переименовывает, перемещает, копирует и удаляет. Он видит, сколько места занято, и может найти нужный файл по имени.

**Независимая проверка**: загрузить набор файлов разного размера, создать вложенную структуру, выполнить переименование, перемещение, копирование и удаление, убедиться, что содержимое и структура соответствуют ожиданиям, а занятое место отражает реальный объём.

**Приёмочные сценарии**:

1. **Given** пустое хранилище, **When** пользователь загружает файл, **Then** файл появляется в указанной папке, доступен для скачивания, а содержимое при скачивании побайтово совпадает с загруженным.
2. **Given** папка с вложенной структурой глубиной несколько уровней, **When** пользователь перемещает её в другую папку, **Then** вся вложенная структура сохраняется, а пути у всех вложенных элементов обновляются.
3. **Given** файл в папке, **When** пользователь копирует его в другую папку, **Then** существуют две независимые копии: изменение одной не влияет на другую.
4. **Given** файл, **When** пользователь удаляет его, **Then** файл исчезает из списка, но остаётся восстановимым из корзины.
5. **Given** заполненное хранилище, **When** пользователь открывает сводку, **Then** он видит использованный объём, доступный остаток и объём, занятый корзиной и версиями, отдельно.

### US-2. Доступ и права — P1

Несколько пользователей работают в одной системе. Владелец файла решает, кто и что с ним может делать: смотреть, комментировать, редактировать, делиться дальше. Администратор управляет учётными записями и группами. Пользователь видит только то, к чему у него есть доступ.

**Независимая проверка**: создать двух пользователей и группу, выдать доступ к папке с разными уровнями и проверить, что каждый видит и может ровно то, что разрешено, а запрещённые действия отклоняются.

**Приёмочные сценарии**:

1. **Given** папка, доступная только владельцу, **When** другой пользователь пытается открыть её, **Then** система не показывает ни её, ни её содержимое и не подтверждает её существование.
2. **Given** пользователь с правом просмотра, **When** он пытается изменить или удалить файл, **Then** действие отклоняется, ответ содержит код причины `forbidden` и рекомендуемое действие, а файл остаётся неизменным.
3. **Given** пользователь с правом редактирования, **When** он загружает новую версию файла, **Then** предыдущая версия сохраняется в истории.
4. **Given** пользователь состоит в группе, **When** группе выдан доступ к папке, **Then** все участники группы получают этот доступ без персональной выдачи.
5. **Given** пользователь исключён из группы, **When** он снова обращается к папке, **Then** доступ, полученный только через группу, отсутствует.

### US-3. Обмен ссылками — P2

Пользователь делится файлом или папкой с человеком, у которого нет учётной записи: создаёт ссылку, при необходимости защищает её паролем и ограничивает сроком действия. Отдельно он может попросить кого-то загрузить файлы в свою папку, не давая доступа к остальному содержимому.

**Независимая проверка**: создать публичную ссылку на файл и на папку, открыть их без входа в систему, проверить пароль, срок действия и отзыв; отдельно проверить ссылку на загрузку.

**Приёмочные сценарии**:

1. **Given** файл, **When** пользователь создаёт публичную ссылку, **Then** ссылка открывается в браузере без входа в систему и позволяет скачать файл.
2. **Given** ссылка, защищённая паролем, **When** открыть её без пароля, **Then** содержимое недоступно; **When** ввести верный пароль, **Then** содержимое доступно.
3. **Given** ссылка со сроком действия, **When** срок истёк, **Then** ссылка перестаёт работать, а владелец видит её как истёкшую.
4. **Given** ссылка на папку, **When** владелец её отзывает, **Then** ссылка немедленно перестаёт работать для всех, кто ею пользовался.
5. **Given** ссылка на загрузку в папку, **When** внешний получатель загружает файл, **Then** файл появляется в папке, а получатель не может просматривать остальное содержимое.

### US-4. Версии и восстановление — P2

Пользователь изменил файл и пожалел об этом: он открывает историю, видит предыдущие версии, сравнивает их и восстанавливает нужную. Удалённое по ошибке он достаёт из корзины. Понимает, как долго всё это хранится.

**Независимая проверка**: создать несколько версий файла, восстановить более раннюю, затем удалить файл, восстановить из корзины и проверить содержимое на каждом шаге.

**Приёмочные сценарии**:

1. **Given** файл с несколькими последовательными изменениями, **When** пользователь открывает историю, **Then** он видит версии с указанием времени и автора каждой.
2. **Given** история версий, **When** пользователь восстанавливает более раннюю версию, **Then** она становится текущей, а восстановленная перед этим версия остаётся в истории.
3. **Given** файл в корзине, **When** пользователь восстанавливает его, **Then** файл возвращается на исходное место, а если исходное место занято — в место, однозначно указывающее на конфликт.
4. **Given** корзина, **When** пользователь очищает её полностью, **Then** система запрашивает подтверждение и после него сообщает, что восстановление невозможно.
5. **Given** истёк срок хранения версии, **When** пользователь открывает историю, **Then** истёкшие версии отсутствуют, а о сроке хранения система сообщает заранее и однозначно.

### US-5. Синхронизация между устройствами — P2

Пользователь держит часть файлов на компьютере, часть — на телефоне. Изменения доезжают до всех устройств. Он может указать, какие папки держать локально, а какие — только по требованию. Он работает и без сети, а когда сеть возвращается, изменения сливаются без потери данных.

**Независимая проверка**: подключить два устройства, изменить файл на одном, убедиться в появлении изменения на другом; отключить сеть, изменить один и тот же файл на обоих, включить сеть и проверить, что ни одна из версий не потеряна.

**Приёмочные сценарии**:

1. **Given** два подключённых устройства, **When** файл изменён на первом, **Then** изменение появляется на втором без ручных действий.
2. **Given** устройство без сети, **When** пользователь изменяет файл, **Then** изменение сохраняется локально и применяется после восстановления связи.
3. **Given** один и тот же файл изменён на двух устройствах без связи, **When** связь восстанавливается, **Then** обе версии сохранены, конфликт обозначен явно, и пользователь может выбрать, какая остаётся основной.
4. **Given** папка, помеченная как «только по требованию», **When** пользователь открывает файл, **Then** файл загружается по требованию, а не хранится локально целиком заранее.
5. **Given** прерванная передача большого файла, **When** связь восстановлена, **Then** передача продолжается с места прерывания, а не начинается заново.

### US-6. Поиск и упорядочивание по смыслу — P3

Пользователь ищет не только по имени: по типу, дате, автору, метке. Он расставляет метки и собственные свойства (например, статус или срок), чтобы затем отобрать нужное. Находит файл, даже если забыл, в какой папке он лежит.

**Независимая проверка**: создать набор файлов с метками и свойствами, выполнить поиск по каждому признаку и по их комбинации, убедиться в точности результатов.

**Приёмочные сценарии**:

1. **Given** файлы с разными метками, **When** пользователь ищет по метке, **Then** результат содержит только помеченные файлы.
2. **Given** файлы, принадлежащие разным пользователям, **When** пользователь выполняет поиск, **Then** результат содержит только те файлы, к которым у него есть доступ.
3. **Given** комбинация условий (тип, дата, метка), **When** пользователь применяет их вместе, **Then** результат удовлетворяет всем условиям одновременно.
4. **Given** файл, переименованный после присвоения метки, **When** пользователь ищет по метке, **Then** файл находится под новым именем.

### US-7. Совместная работа — P3

Пользователи обсуждают файл: оставляют комментарии, отвечают на них, упоминают коллег и видят, что появилось нового. Для документов, которые нужно править вместе, система позволяет работать над одним файлом одновременно, не создавая конфликтующих копий.

**Независимая проверка**: оставить комментарий к файлу, ответить на него, упомянуть пользователя и проверить уведомление и признак непрочитанного; отдельно — одновременное редактирование одного документа двумя пользователями.

**Приёмочные сценарии**:

1. **Given** файл, **When** пользователь оставляет комментарий, **Then** комментарий виден всем, у кого есть доступ к файлу, с указанием автора и времени.
2. **Given** комментарий, **When** другой пользователь отвечает на него, **Then** ответ отображается в той же ветке, а автор исходного комментария получает уведомление.
3. **Given** упоминание пользователя в комментарии, **When** комментарий сохранён, **Then** упомянутый получает уведомление, даже если не открывал файл.
4. **Given** документ, **When** два пользователя редактируют его одновременно, **Then** изменения обоих применяются без создания конфликтующих копий, а участники видят друг друга как редактирующих.

### US-8. Администрирование и контроль — P3

Администратор управляет учётными записями и группами, задаёт квоты и политики хранения, видит, что происходит в системе. Пользователь понимает, какие правила к нему применяются, и не удивляется, когда упрётся в квоту.

**Независимая проверка**: задать квоту пользователю, превысить её, проверить отказ и сообщение; выполнить административное действие и найти его в журнале.

**Приёмочные сценарии**:

1. **Given** пользователь с квотой, **When** загрузка превысит остаток, **Then** загрузка отклоняется, а сообщение указывает, сколько осталось и что можно освободить.
2. **Given** административное действие (блокировка пользователя, изменение квоты, изменение политики), **When** оно выполнено, **Then** запись о нём появляется в журнале с указанием кто, что и когда.
3. **Given** заблокированный пользователь, **When** он пытается войти, **Then** доступ отклоняется, а его данные остаются в системе согласно политике хранения.
4. **Given** политика хранения корзины, **When** задан срок, **Then** пользователь видит этот срок и не может рассчитывать на более долгое хранение.

### US-9. Доступ из сторонних средств и внешние хранилища — P3

Пользователь подключает хранилище к привычным инструментам и, при необходимости, подключает к системе уже существующие внешние хранилища, чтобы видеть их рядом со своими файлами.

**Независимая проверка**: подключить сторонний клиент и выполнить в нём чтение и запись; подключить внешнее хранилище и убедиться, что его содержимое доступно наравне с локальным.

**Приёмочные сценарии**:

1. **Given** настроенный доступ из стороннего средства, **When** пользователь читает и записывает файлы, **Then** изменения отражаются в системе так же, как при работе через основной интерфейс.
2. **Given** подключённое внешнее хранилище, **When** пользователь открывает его, **Then** он видит его содержимое в общей структуре, а права внешнего хранилища соблюдаются.
3. **Given** внешнее хранилище стало недоступно, **When** пользователь открывает его, **Then** система сообщает о недоступности, не теряя остальные данные и не показывая пустоту как факт.

### US-10. Обмен между разными установками — P3

Две организации (или два личных экземпляра) хотят делиться папками напрямую, без переноса данных через третью сторону.

**Независимая проверка**: связать две установки, выдать доступ к папке и проверить, что другая сторона видит и получает ровно выданное.

**Приёмочные сценарии**:

1. **Given** две связанные установки, **When** пользователь первой выдаёт доступ к папке пользователю второй, **Then** получатель видит папку и работает с ней согласно выданным правам.
2. **Given** связь отозвана, **When** получатель обращается к папке, **Then** доступ отсутствует, а ранее скопированные им данные остаются у него.

### US-11. Сквозное шифрование папки — P2

Пользователь хочет, чтобы содержимое отдельной папки не мог прочитать никто, кроме владельца и тех, кому он доверил ключ — включая администратора системы. Он включает шифрование на папке, заранее видит, какие возможности при этом потеряет, и подтверждает решение осознанно. После включения сервер хранит только нечитаемые данные.

**Независимая проверка**: включить шифрование на папке с несколькими файлами, убедиться, что предупреждение показано до подтверждения, поиск по содержимому внутри неё не находит ничего, серверная выгрузка даёт нечитаемые данные, а отключить шифрование невозможно.

**Приёмочные сценарии**:

1. **Given** обычная папка, **When** пользователь выбирает включение шифрования, **Then** до подтверждения ему показан перечень возможностей, которые станут недоступны, и требуется явное согласие.
2. **Given** папка с шифрованием, **When** пользователь ищет по фразе, которая точно есть в одном из её файлов, **Then** результат пуст: содержимое таких папок не индексируется.
3. **Given** папка с шифрованием, **When** администратор системы пытается прочитать содержимое файла без ключа пользователя, **Then** он получает нечитаемые данные, а не открытый файл.
4. **Given** папка с шифрованием, **When** пользователь пытается отключить шифрование, **Then** действие отклоняется как неподдерживаемое, а данные остаются зашифрованными.
5. **Given** папка, внутри которой уже есть незашифрованные объекты, **When** пользователь пытается включить шифрование, **Then** действие отклоняется с объяснением, что смешивать зашифрованное и незашифрованное в одной папке нельзя.

### US-12. Выгрузка учётной записи — P3

Пользователь хочет забрать все свои данные одним действием, не собирая файлы по одному: получить архив со всей структурой папок и сведениями о файлах. Он понимает, что именно скачивает, и знает, сколько времени архив будет доступен.

**Независимая проверка**: запросить выгрузку учётной записи с вложенной структурой, дождаться готовности, скачать архив и сверить, что все файлы и папки присутствуют с сохранением путей, а метаданные приложены отдельно.

**Приёмочные сценарии**:

1. **Given** учётная запись с файлами и вложенными папками, **When** пользователь запрашивает полную выгрузку, **Then** формируется один архив, содержащий все его файлы с сохранением структуры папок.
2. **Given** выгрузка выполняется, **When** архив готов, **Then** пользователь получает уведомление с указанием объёма и состава архива до начала скачивания.
3. **Given** в учётной записи есть папка с шифрованием, **When** выполняется выгрузка, **Then** её файлы попадают в архив в зашифрованном виде и не расшифровываются системой.
4. **Given** архив был сформирован, **When** истекает срок его хранения, **Then** архив удаляется и больше не может быть скачан.

## 5. Функциональные требования

### 5.1. Учётные записи, доступ и права

- **FR-001**: Система MUST позволять создавать, изменять, блокировать и удалять учётные записи пользователей; удаление учётной записи MUST сохранять её данные согласно FR-101…FR-104.
- **FR-002**: Система MUST поддерживать группы пользователей и включение пользователя в несколько групп одновременно.
- **FR-003**: Система MUST различать как минимум уровни доступа: просмотр, комментирование, редактирование, полный контроль (включая передачу прав и удаление).
- **FR-004**: Система MUST предоставлять доступ как отдельным пользователям, так и группам, и вычислять итоговые права по совокупности выданных.
- **FR-005**: Система MUST запрещать действия, на которые у пользователя нет прав, и сообщать об отказе так, чтобы ответ содержал машиночитаемый код причины и рекомендуемое действие, не раскрывая существование недоступных объектов.
- **FR-006**: Система MUST поддерживать передачу владения объектом другому пользователю.
- **FR-007**: Система MUST завершать активные сеансы пользователя при блокировке или смене пароля в течение не более 60 секунд.
- **FR-008**: Пользователь MUST видеть перечень объектов, к которым ему выдан доступ, и перечень объектов, которыми он поделился.

### 5.2. Файлы и папки

- **FR-009**: Система MUST поддерживать создание, чтение, изменение, переименование, перемещение, копирование и удаление файлов и папок.
- **FR-010**: Система MUST поддерживать вложенность папок не менее 32 уровней и полный путь длиной до 4096 символов; попытка превысить любой из пределов MUST отклоняться с ошибкой, указывающей предел и текущее значение.
- **FR-011**: Система MUST сохранять содержимое файла без искажений: скачанный файл MUST совпадать с загруженным.
- **FR-012**: Система MUST обеспечивать однозначность путей: два объекта с одинаковым именем в одной папке недопустимы.
- **FR-013**: Система MUST предоставлять сведения о каждом объекте: имя, размер, тип, время создания, время последнего изменения, владелец, текущие права.
- **FR-014**: Система MUST сохранять исходное время изменения файла при загрузке и синхронизации.
- **FR-015**: Система MUST позволять массовые операции над набором объектов с сообщением о ходе выполнения.
- **FR-016**: Система MUST поддерживать перемещение и копирование папок целиком с сохранением вложенной структуры.
- **FR-017**: Система SHOULD предупреждать пользователя, если имя объекта изменено из-за несовместимости с правилами целевого клиента, и указывать, как оно было изменено.
- **FR-018**: Система MUST отклонять операции, приводящие к циклической вложенности (папка внутрь самой себя).

### 5.3. Передача файлов

- **FR-019**: Система MUST поддерживать загрузку и скачивание файлов, превышающих типичные ограничения одной операции.
- **FR-020**: Система MUST возобновлять прерванную передачу с места прерывания, не требуя повторной передачи уже переданной части.
- **FR-021**: Система MUST показывать ход передачи: объём переданного, оставшееся время либо объём, и текущую скорость.
- **FR-022**: Система MUST позволять приостановить и продолжить передачу.
- **FR-023**: Система MUST помечать файл как доступный только после полного завершения передачи; частично переданные данные MUST NOT отображаться как готовый файл.
- **FR-024**: Система MUST обнаруживать повреждение при передаче и повторять передачу повреждённой части.
- **FR-025**: Система MUST поддерживать передачу множества файлов одновременно с ограничением числа параллельных операций, настраиваемым пользователем.
- **FR-026**: Система MUST сообщать о причине неудачи передачи и о том, можно ли её возобновить.

### 5.4. Версии и корзина

- **FR-027**: Система MUST сохранять предыдущую версию файла при каждой замене содержимого.
- **FR-028**: Система MUST показывать историю версий с указанием автора и времени каждой версии.
- **FR-029**: Система MUST позволять восстановить любую сохранённую версию, делая её текущей без удаления остальных версий.
- **FR-030**: Система MUST позволять скачать любую сохранённую версию.
- **FR-031**: Система MUST хранить удалённые объекты в корзине и позволять восстановление на исходное место.
- **FR-032**: Система MUST поддерживать настраиваемые сроки хранения версий и корзины и сообщать пользователю действующие значения.
- **FR-033**: Система MUST запрашивать подтверждение перед окончательным удалением и сообщать, что восстановление после него невозможно.
- **FR-034**: Система MUST при восстановлении объекта в занятое место создавать однозначно обозначенную копию, а не перезаписывать существующий объект.
- **FR-035**: Система MUST учитывать объём, занятый версиями и корзиной, отдельно от объёма текущих файлов при расчёте квоты.

### 5.5. Ссылки и внешний доступ

- **FR-036**: Система MUST создавать публичные ссылки на файлы и папки, доступные без учётной записи.
- **FR-037**: Система MUST позволять защищать ссылку паролем.
- **FR-038**: Система MUST позволять ограничивать срок действия ссылки и отзывать её в любой момент.
- **FR-039**: Система MUST позволять создавать ссылки на загрузку в папку без предоставления доступа к её содержимому.
- **FR-040**: Система MUST прекращать действие ссылки при удалении объекта и сообщать получателю о причине недоступности.
- **FR-041**: Система MUST показывать владельцу перечень активных ссылок с возможностью отзыва.
- **FR-042**: Система SHOULD позволять ограничивать число скачиваний по ссылке, если такая политика задана.
- **FR-043**: Система MUST NOT раскрывать через публичную ссылку сведения о других объектах хранилища.

### 5.6. Синхронизация

- **FR-044**: Система MUST синхронизировать изменения между несколькими устройствами одного пользователя без ручных действий.
- **FR-045**: Система MUST поддерживать работу без сети с последующим применением накопленных изменений.
- **FR-046**: Система MUST сохранять обе версии при конфликте и обозначать конфликт явно; молчаливый выбор победителя, приводящий к потере данных, MUST NOT применяться.
- **FR-047**: Система MUST определять порядок изменений независимо от расхождения системного времени устройств.
- **FR-048**: Система MUST поддерживать выборочную синхронизацию: пользователь указывает, какие папки хранить локально.
- **FR-049**: Система MUST поддерживать доступ к файлам по требованию без предварительной полной загрузки.
- **FR-050**: Система MUST корректно обрабатывать переименование и перемещение объекта на одном устройстве без его повторной полной передачи на других.
- **FR-051**: Система MUST сообщать пользователю о состоянии синхронизации каждого объекта: синхронизирован, ожидает, конфликт, ошибка.
- **FR-052**: Система MUST соблюдать правила регистра и допустимых имён целевого устройства, предотвращая потерю объектов при переносе между системами с разными правилами.

### 5.7. Метаданные и поиск

- **FR-053**: Система MUST позволять назначать объектам метки.
- **FR-054**: Система MUST позволять задавать пользовательские свойства объекта (имя свойства и значение) и отбирать объекты по ним.
- **FR-055**: Система MUST поддерживать поиск по имени, типу, размеру, дате, владельцу и меткам.
- **FR-056**: Система MUST ограничивать результаты поиска только объектами, к которым у пользователя есть доступ.
- **FR-057**: Система MUST сохранять метки и свойства при переименовании и перемещении объекта.
- **FR-058**: Система SHOULD поддерживать сохранённые условия отбора для повторного использования.
- **FR-059**: Система MUST поддерживать поиск по содержимому текстовых документов, если сквозное шифрование не включено.

### 5.8. Комментарии и уведомления

- **FR-060**: Система MUST позволять оставлять комментарии к объектам, видимые всем, у кого есть доступ.
- **FR-061**: Система MUST поддерживать ветки ответов на комментарии.
- **FR-062**: Система MUST поддерживать упоминание пользователя в комментарии с отправкой уведомления упомянутому.
- **FR-063**: Система MUST показывать пользователю признак наличия непрочитанных изменений и уведомлений.
- **FR-064**: Система SHOULD позволять пользователю настраивать, о каких событиях он получает уведомления.
- **FR-065**: Система MUST сохранять комментарии при переименовании и перемещении объекта и удалять их вместе с объектом.

### 5.9. Совместное редактирование

- **FR-066**: Система SHOULD поддерживать одновременное редактирование одного документа несколькими пользователями без создания конфликтующих копий.
- **FR-067**: Система SHOULD показывать участникам, кто ещё работает с документом в данный момент.
- **FR-068**: Система SHOULD сохранять изменения при разрыве связи у одного из участников и применять их после восстановления.
- **FR-069**: Система SHOULD сохранять результат совместного редактирования как новую версию в истории.

### 5.10. Квоты, администрирование и аудит

- **FR-070**: Система MUST назначать квоты пользователям и группам и обеспечивать их соблюдение.
- **FR-071**: Система MUST сообщать пользователю использованный объём, остаток и состав занятого места (файлы, версии, корзина).
- **FR-072**: Система MUST отклонять операции, превышающие квоту, с указанием, сколько не хватает и что можно освободить.
- **FR-073**: Система MUST вести журнал административных и значимых действий с указанием кто, что, когда и над каким объектом.
- **FR-074**: Система MUST позволять задавать политики хранения для версий и корзины на уровне системы и на уровне пользователя.
- **FR-075**: Система MUST позволять администратору ограничивать типы файлов и максимальный размер отдельного файла, если такая политика задана.
- **FR-076**: Система MUST позволять администратору видеть состояние системы: число пользователей, занятый объём, ошибки.
- **FR-077**: Система MUST ограничивать доступ к административным функциям отдельной ролью.

### 5.11. Внешние хранилища и интеграция

- **FR-078**: Система MUST позволять подключать внешние хранилища и отображать их содержимое в общей структуре.
- **FR-079**: Система MUST соблюдать права внешнего хранилища при работе с подключённым содержимым.
- **FR-080**: Система MUST сообщать о недоступности внешнего хранилища, не показывая его пустым и не блокируя остальные данные.
- **FR-081**: Система MUST предоставлять доступ к файлам из сторонних клиентских средств на чтение и запись.
- **FR-082**: Система SHOULD поддерживать получение уведомлений о событиях внешними системами.

### 5.12. Обмен между установками

- **FR-083**: Система SHOULD позволять связывать отдельные установки и выдавать доступ к объектам между ними.
- **FR-084**: Система SHOULD обеспечивать отзыв такого доступа, при котором ранее переданные получателю копии остаются у него, но новый доступ прекращается.
- **FR-085**: Система SHOULD уведомлять пользователя о том, что объект получен из другой установки, и о том, кто им управляет.

### 5.13. Идентификация и защита доступа

- **FR-086**: Система MUST аутентифицировать пользователей и MUST NOT допускать доступа к данным без успешной аутентификации.
- **FR-087**: Система MUST поддерживать многофакторную аутентификацию.
- **FR-088**: Система SHOULD поддерживать вход через внешнего поставщика идентификации, если он настроен администратором.
- **FR-089**: Система MUST поддерживать сквозное шифрование содержимого, при котором сервер не имеет доступа к открытым данным.
- **FR-090**: Система MUST явно сообщать пользователю до включения шифрования, что для зашифрованных объектов становятся недоступны как минимум: поиск по содержимому (FR-059), предпросмотр без скачивания, совместное редактирование (FR-066…FR-069) и возобновляемая загрузка через веб-интерфейс.
- **FR-091**: Система MUST сохранять возможность восстановления доступа к зашифрованным данным при утере пароля или ключа ровно в той мере, в какой это было явно выбрано пользователем при настройке; если восстановление невозможно, это MUST быть сообщено до включения шифрования.
- **FR-092**: Система MUST NOT ослаблять сквозное шифрование ради других возможностей без явного действия пользователя.

### 5.14. Сохранность данных и восстановление

- **FR-093**: Система MUST регулярно создавать резервную копию пользовательских данных и метаданных; периодичность MUST обеспечивать потерю при сбое не более чем за последние сутки.
- **FR-094**: Система MUST восстанавливаться до рабочего состояния не более чем за 4 часа после сбоя, при котором данные или работоспособность были утрачены.
- **FR-095**: Система MUST обеспечивать проверку пригодности резервной копии к восстановлению без разрушения текущих данных; результат проверки MUST быть наблюдаем администратору.
- **FR-096**: Система MUST сообщать администратору о неудачном создании или проверке резервной копии.
- **FR-097**: Система MUST NOT полагаться на резервную копию как на замену журналу версий и корзине: восстановление из копии и восстановление пользователем — разные механизмы, и оба MUST работать независимо.
- **FR-098**: Система MUST позволять пользователю выгрузить всё содержимое своей учётной записи одним действием, с сохранением структуры папок и метаданных объектов.
- **FR-099**: Система MUST сообщать о готовности выгрузки, её объёме и о том, что она содержит, до начала скачивания.
- **FR-100**: Система MUST NOT требовать ручного сбора файлов по одному для полной выгрузки учётной записи.
- **FR-101**: Система MUST при удалении учётной записи сохранять её данные и блокировать доступ, а не удалять содержимое автоматически.
- **FR-102**: Система MUST позволять администратору передать владение сохранёнными данными заблокированного пользователя другому пользователю.
- **FR-103**: Система MUST удалять данные заблокированного пользователя только по явному административному действию с подтверждением и записью в журнале.
- **FR-104**: Система MUST сохранять доступность общих объектов для остальных участников при блокировке учётной записи их владельца; владение MUST быть передано до окончательного удаления данных.

## 6. Краевые случаи

Перечислены ситуации, которые обычно теряются при составлении требований и всплывают как переделки. Для каждой определена позиция.

1. **Конфликт версий при синхронизации**: один файл изменён на двух устройствах без связи. Обе версии сохраняются; конфликт обозначается явно; автоматическое «побеждает последний» недопустимо, если оно приводит к молчаливой потере.
2. **Разрешение конфликта не по времени**: системное время устройств может расходиться, поэтому порядок изменений не может определяться только отметкой времени.
3. **Совпадение имён с разным регистром**: `Отчёт.txt` и `отчёт.txt` одновременно. Система не различает такие имена в пределах одной папки: второе имя отклоняется с ошибкой `name_conflict`, а при синхронизации файлы не теряются.
4. **Недопустимые имена**: символы, запрещённые на одной из платформ-клиентов, и служебные имена. Имя сохраняется без потери данных, а пользователь предупреждается, если имя изменено; предупреждение содержит исходное и итоговое имя.
5. **Очень большой файл**: файл, сравнимый с квотой или превышающий типичные ограничения отдельной операции. Загрузка не должна «зависать» без обратной связи; возобновление должно работать.
6. **Прерывание передачи**: обрыв связи, закрытие клиента, перезагрузка. Частично переданные данные не должны выглядеть как полноценный файл.
7. **Файл ещё не готов, а уже читается**: сразу после завершения загрузки метаданные могут быть доступны раньше, чем содержимое. Чтение в этот момент не должно давать ошибку или повреждённый результат.
8. **Изменение времени файла без изменения содержимого**: должно быть возможно и не должно приводить к ложным конфликтам.
9. **Дубликаты имён в одной папке**: система не допускает неоднозначности в путях.
10. **Удаление папки, на которую есть ссылка или общий доступ**: получатели получают ответ с кодом `not_found` и указанием, что объект удалён, а не пустую страницу без объяснения.
11. **Удаление файла, открытого у другого пользователя**: удаление разрешено. Пользователь, у которого файл открыт, получает уведомление при следующем обращении к системе; если он успел изменить содержимое, его изменения сохраняются отдельной копией и не теряются.
12. **Исчерпание квоты посреди синхронизации**: изменения не должны теряться молча; пользователь должен узнать, что именно не сохранилось.
13. **Огромная папка**: количество элементов, при котором массовые операции (перемещение, удаление, копирование) перестают быть мгновенными. Система сообщает о ходе и не обрывается без объяснения.
14. **Слишком длинный путь и глубокая вложенность**: поддерживается глубина до 32 уровней и полный путь до 4096 символов; попытка превысить предел завершается ошибкой с указанием предела и текущей глубины или длины.
15. **Одновременное редактирование и версионирование**: правка, пришедшая во время очистки истории, не должна приводить к потере текущего содержимого.
16. **Смена пароля или отзыв доступа**: активные сеансы завершаются в течение не более 60 секунд, а отозванные ссылки перестают работать немедленно.
17. **Часовые пояса и переходы времени**: отображение времени не должно сбивать; порядок версий не должен зависеть от пояса.
18. **Шифрование на стороне пользователя против серверных возможностей**: при включении сквозного шифрования часть возможностей (поиск по содержимому, предпросмотр, совместное редактирование, возобновляемая загрузка в веб-интерфейсе) становится недоступной. Конфликт фиксируется как открытое решение, а не разрешается молча.

## 7. Критерии приёмки

### 7.1. Наблюдаемое поведение системы

- **SC-001**: Пользователь может загрузить файл и получить его обратно без искажений в 100% случаев при отсутствии ошибок передачи; проверяется сравнением содержимого.
- **SC-002**: Загрузка файла, размер которого превышает типичные ограничения одной операции, завершается успешно и после обрыва продолжается с места прерывания, а не начинается заново.
- **SC-003**: Ни один сценарий конфликта синхронизации не приводит к потере данных: после конфликта существуют обе версии, и это проверяется на всех перечисленных в разделе 6 случаях.
- **SC-004**: Пользователь без прав не может получить доступ к объекту ни через интерфейс, ни через ссылку, ни через сторонний клиент — 0 успешных попыток в проверочном наборе.
- **SC-005**: Восстановление удалённого объекта и восстановление предыдущей версии возвращают содержимое, побайтово совпадающее с ожидаемым, в 100% проверок.
- **SC-006**: Отзыв ссылки прекращает доступ немедленно: после отзыва 0 успешных обращений.
- **SC-007**: Пользователь может найти объект по любому из поддерживаемых признаков (имя, тип, дата, владелец, метка, свойство) и по их комбинации; точность проверяется на подготовленном наборе, ложных положительных результатов — 0.
- **SC-008**: При превышении квоты операция отклоняется, а сообщение называет остаток и способ освободить место; молчаливой потери данных — 0 случаев.
- **SC-009**: Каждое административное действие обнаруживается в журнале с указанием кто, что и когда; пропусков — 0.
- **SC-010**: Одновременное редактирование одного документа двумя пользователями не создаёт конфликтующих копий и не теряет изменения ни одного из них.
- **SC-016**: Система выполняет все перечисленные требования при заявленном масштабе: до 10 пользователей, до 1 ТБ суммарного объёма, до 10 000 объектов в одной папке; выход за эти пределы MUST отклоняться или сообщаться явно, а не приводить к ошибке без объяснения.
- **SC-017**: При сбое, приведшем к утрате данных или работоспособности, потеря данных не превышает последних суток, а восстановление до рабочего состояния занимает не более 4 часов; проверяется учебным восстановлением из резервной копии.
- **SC-018**: Каждая созданная резервная копия проверена на пригодность к восстановлению, а о любой неудаче создания или проверки администратор узнаёт без ручного поиска; непроверенных копий — 0.
- **SC-019**: При заявленном масштабе система отвечает в установленные сроки: открытие папки с 1 000 объектов — до 2 секунд; видимая реакция на действие пользователя — до 0,5 секунды; поиск — до 2 секунд; начало скачивания — до 3 секунд. Проверяется на подготовленном наборе данных; доля замеров, укладывающихся в планку, — не менее 95%.
- **SC-020**: Пользователь может выгрузить всю свою учётную запись одним действием, и выгруженный набор содержит все его файлы и папки с сохранением структуры; проверяется сравнением состава и путей. Доля файлов, отсутствующих в выгрузке, — 0.
- **SC-021**: После блокировки учётной записи её данные остаются доступны администратору и не исчезают; общие объекты остаются доступны остальным участникам в 100% проверок. Автоматического удаления данных при блокировке — 0 случаев.
- **SC-022**: Передача владения от заблокированного пользователя другому пользователю сохраняет состав и пути переданных объектов; потерь при передаче — 0.
- **SC-023**: Ни один файл в папке со сквозным шифрованием не может быть прочитан средствами системы без ключа пользователя: попытка чтения на стороне системы возвращает нечитаемые данные, а поиск по содержимому внутри такой папки возвращает 0 результатов. Доля расшифрованных системой файлов — 0.

### 7.2. Полнота и пригодность самого документа

- **SC-011**: Все области из US-1…US-12 описаны требованиями; для каждой области есть хотя бы один сценарий и хотя бы одно проверяемое требование. Доля областей без требований — 0.
- **SC-012**: Каждое требование отнесено к обязательному (MUST) или желательному (SHOULD); исключённые возможности перечислены с причиной. Требований без классификации — 0.
- **SC-013**: Каждый краевой случай из раздела 6 имеет явную позицию: требование, сценарий или обоснованное исключение. Краевых случаев без позиции — 0.
- **SC-014**: Содержательная часть не содержит технологических решений (языков, СУБД, протоколов, продуктов, форматов хранения). Проверяется формально.
- **SC-015**: По документу можно начать реализацию, не возвращаясь к вопросу «а что вообще должно быть»; проверяется тем, что каждое требование допускает проверку без уточнений.

## 8. Границы: что сознательно не входит

Перечислено, чтобы границы были видимы. Отказ обоснован, а не забыт.

- **Полнотекстовый поиск по изображениям, аудио и видео (распознавание содержимого)** — выходит за пределы функциональных требований к хранению; требует отдельного класса возможностей.
- **Встроенный офисный пакет как продукт** — совместное редактирование описано как требование (FR-066…FR-069), но собственный редактор документов не является частью хранилища.
- **Антивирусная проверка и защита от утечек** — политика безопасности уровня организации, а не свойство хранилища; при необходимости — отдельная область.
- **Биллинг, тарифы, платёжные операции** — для описываемой системы не заявлены.
- **Мобильные приложения как отдельный продукт** — требования к синхронизации (US-5) платформенно-нейтральны; наличие конкретных приложений — вопрос реализации.
- **Аналитика использования и отчётность для руководства** — не заявлена.
- **Публикация в общий каталог и маркетплейс расширений** — не заявлена.
- **Импорт из другого хранилища с сохранением структуры и метаданных** — полная выгрузка требуется (FR-098…FR-100), обратный импорт — нет. При необходимости это отдельная задача, а не недоделанная часть этой.

## 9. Допущения и принятые решения

### 9.1. Допущения

- **Система многопользовательская.** Требования к правам, группам, квотам и совместной работе предполагают несколько пользователей. Для одного пользователя они вырождаются, но не мешают.
- **Пользователи работают с устройств под управлением распространённых настольных и мобильных систем.** Требования к синхронизации, именам и регистру сформулированы платформенно-нейтрально, но предполагают клиенты на нескольких платформах с разными правилами имён.
- **Сеть может быть медленной, нестабильной и отсутствовать.** Отсюда требования к возобновлению передач, офлайну и явным конфликтам.
- **Файлы бывают очень большими и очень многочисленными.** Верхняя граница размера отдельного файла ограничена только квотой (FR-070, FR-072).
- **Данные пользователя ценны и невосстановимы.** Приоритет — не потерять данные, даже ценой удобства: конфликт обозначается, а не разрешается молча.
- **Внешние хранилища и сторонние клиенты — расширения, а не ядро.** При их отсутствии система сохраняет базовую ценность.
- **Технологии не выбираются на этом этапе.** Любое требование, которое невозможно выполнить без выбора технологии, решается на этапе планирования.
- **Ограничения конкретных продуктов не являются требованиями.** Если возможность отсутствует у одного из референсов, это не означает, что она не нужна; если присутствует — не означает, что нужна.

### 9.2. Принятые решения

| Решение | Значение | Основание |
|---|---|---|
| Масштаб | до 10 пользователей, до 1 ТБ, до 10 000 объектов в папке | заявленная область применения |
| Сроки хранения по умолчанию | версии — 30 дней и не более 100 версий на файл; корзина — 30 дней | настраивается администратором |
| Сквозное шифрование | обязательная возможность, не режим по умолчанию; необратимо на папку | FR-089…FR-092 |
| Совместное редактирование | желательная возможность (SHOULD), не ядро | FR-066…FR-069 |
| Обмен между установками | желательная возможность (SHOULD) | FR-083…FR-085 |
| Удаление учётной записи | блокировка с сохранением данных; передача владения или явное удаление | FR-101…FR-104 |
| Импорт из другого хранилища | не требуется | раздел 8 |

### 9.3. Открытые решения

1. **Класс документов для совместного редактирования** не зафиксирован. Требование описывает поведение, но не перечень форматов.
2. **Значение квоты по умолчанию** остаётся настройкой и в документе не фиксируется.
3. **Свежесть сведений о референсах.** Часть данных о Яндекс.Диске, Google Drive и Dropbox получена из документации открытых проектов и спецификаций интерфейсов; сайты поставщиков в момент подготовки были недоступны. При реализации требования перепроверяются.

## 10. Источники требований

Требования выведены из анализа возможностей существующих систем и их открытых аналогов:

- **Яндекс.Диск, Google Drive, Dropbox** — референсные продукты, задающие ожидаемый набор возможностей.
- **Nextcloud, ownCloud (Classic и Infinite Scale), Seafile** — открытые реализации, по которым проверялась полнота областей и краевых случаев.
- **rclone** — матрица различий между хранилищами (хеши, точность времени, регистр, ограничения имён, лимиты операций), использованная как чек-лист функциональных осей.
- **tus** — стандарт возобновляемой загрузки.
- **Cryptomator** — модель клиентского шифрования поверх чужого хранилища.
- **Dropbox API Spec** — карта функциональных доменов зрелого продукта.

Ограничения конкретных продуктов **не переносились** как требования. Например, лимит «30 дней или 100 ревизий» у Google Drive — продуктовое решение, а не закономерность; в этом документе сроки хранения заданы как настраиваемые значения с явно выбранными значениями по умолчанию.
